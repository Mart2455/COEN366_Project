# CENRS Protocol

This document defines the messages exchanged between CENRS clients and the Emergency Server.

The required message names and fields come from the project specification. The pipe-separated representation and the detailed rules below are the team's chosen protocol design.

## Message encoding

- Control messages use UTF-8 text.
- Fields are separated using `|`.
- Spaces are allowed inside fields.
- A field cannot contain `|`, `\r`, or `\n`.
- Message names and enum values are uppercase.
- Lists contain comma-separated values.
- Each UDP datagram contains exactly one complete message.
- Each TCP control message ends with a newline character.
- UDP messages and TCP headers cannot exceed 4096 bytes.

Field limits are measured after UTF-8 encoding:

- Name: 64 bytes
- Title: 128 bytes
- Description: 1024 bytes
- Reason: 256 bytes
- File name: 255 bytes

## Request numbers

`RQ#` is a positive 64-bit number generated by the sender.

- Each sender maintains an increasing request counter.
- A response copies the `RQ#` from its request.
- A retransmission reuses the original `RQ#`.
- A request is identified using the sender and `RQ#` together.
- Repeating a request must not repeat the state change.
- The receiver returns the previous response when it recognizes a duplicate request.

## Registration

A client registers through UDP using:

```text
REGISTER|RQ#|Name|Role|IP_Address|UDP_Port|TCP_Port
```

Example:

```text
REGISTER|01|Alice|SUBSCRIBER|192.168.1.10|5001|6001
```

Valid roles are:

```text
SUBSCRIBER
PUBLISHER
BOTH
```

Each registered name must be unique. `UDP_Port` is used for control messages, notifications, and acknowledgements. `TCP_Port` is used for attachment transfer and synchronization.

The server uses the UDP datagram's source address as the sender's identity. The address and UDP port declared in `REGISTER` must match the datagram source.

If registration succeeds:

```text
REGISTERED|RQ#|Location_List|Category_List
```

Example:

```text
REGISTERED|01|HALL,EV,JMSB,LOYOLA,SGW,ALL|FIRE,SECURITY,WEATHER,POWER,BUILDING,GENERAL,ALL
```

The project PDF uses `REGISTER` in one response example. Issue #3 resolves this typo in favor of `REGISTERED`.

If registration fails:

```text
REGISTER-DENIED|RQ#|Reason
```

Example:

```text
REGISTER-DENIED|01|Name already exists
```

A registered client leaves the system using:

```text
DE-REGISTER|RQ#|Name
```

Example:

```text
DE-REGISTER|14|Alice
```

The server removes the client if it exists. If it does not exist, the server ignores the request. No separate success response is sent.

## Subscriptions

A registered `SUBSCRIBER` or `BOTH` client creates a subscription using:

```text
SUBSCRIBE|RQ#|Location|Category
```

Example:

```text
SUBSCRIBE|21|HALL|FIRE
```

A client may maintain multiple subscriptions. The same location and category pair is stored only once.

If accepted:

```text
SUBSCRIBED|RQ#
```

Example:

```text
SUBSCRIBED|21
```

If rejected:

```text
SUBSCRIPTION-DENIED|RQ#|Reason
```

Example:

```text
SUBSCRIPTION-DENIED|21|Invalid category
```

A client removes a subscription using:

```text
UNSUBSCRIBE|RQ#|Location|Category
```

Example:

```text
UNSUBSCRIBE|35|HALL|FIRE
```

The server removes the matching subscription. No separate success response is sent.

The initial locations are:

```text
HALL, EV, JMSB, LOYOLA, SGW, ALL
```

The categories are:

```text
FIRE, SECURITY, WEATHER, POWER, BUILDING, GENERAL, ALL
```

`ALL` is a wildcard. An alert for `HALL/FIRE` matches:

```text
HALL/FIRE
ALL/FIRE
HALL/ALL
ALL/ALL
```

## Publishing an incident

A registered `PUBLISHER` or `BOTH` client creates an incident through UDP using:

```text
PUBLISH_ALERT|RQ#|Category|Location|Severity|Title|Description|Attachment
```

Example:

```text
PUBLISH_ALERT|45|FIRE|HALL|CRITICAL|Fire Alarm|Evacuate the building|evacuation_map.pdf
```

Valid severity levels are:

```text
INFO
WARNING
CRITICAL
```

`Attachment` is either `NONE` or the name of a file stored by the publisher. The Emergency Server stores the attachment name and publisher information, but not the file contents.

If accepted, the server creates a globally unique `Incident_ID`. A new incident starts with Version `1` and Status `ACTIVE`.

```text
ALERT_ACCEPTED|RQ#|Incident_ID
```

Example:

```text
ALERT_ACCEPTED|45|INC102
```

If rejected:

```text
ALERT_DENIED|RQ#|Reason
```

Example:

```text
ALERT_DENIED|45|Unauthorized role
```

`RQ#` identifies a protocol request. `Incident_ID` identifies an incident throughout its lifetime.

## Alert distribution

The server sends an alert to every registered subscriber whose subscriptions match the incident:

```text
ALERT|RQ#|Incident_ID|Version|Category|Location|Severity|Title|Description|Attachment
```

Example:

```text
ALERT|83|INC102|1|FIRE|HALL|CRITICAL|Fire Alarm|Evacuate the building|evacuation_map.pdf
```

The server generates a separate `RQ#` for each outgoing notification. Every subscriber receives the same `Incident_ID` and Version for the same incident state.

## Critical alert acknowledgements

A subscriber acknowledges a `CRITICAL` alert using:

```text
ALERT_ACK|RQ#|Incident_ID|Version|Name
```

Example:

```text
ALERT_ACK|83|INC102|1|Alice
```

The acknowledgement uses the same `RQ#` as the received alert.

The acknowledgement timeout is configurable, with a default of two seconds. If no valid acknowledgement is received, the server retransmits the same alert.

The server makes a maximum of three total transmission attempts. After the third unsuccessful attempt, it records the delivery as `UNCONFIRMED` and continues serving other clients.

A subscriber identifies a duplicate using `Incident_ID` and Version. It acknowledges the duplicate again but does not display or process it as a new alert.

`INFO` and `WARNING` alerts do not require acknowledgements.

## Updating an incident

Only the publisher that created an active incident may update it.

```text
UPDATE_ALERT|RQ#|Incident_ID|Severity|Title|Description
```

Example:

```text
UPDATE_ALERT|71|INC102|WARNING|Fire Controlled|Remain outside the building
```

If accepted, the server increments the Version and responds:

```text
ALERT_UPDATED|RQ#|Incident_ID|Version
```

Example:

```text
ALERT_UPDATED|71|INC102|2
```

The server sends the update to matching subscribers:

```text
ALERT_UPDATE|RQ#|Incident_ID|Version|Severity|Title|Description
```

Example:

```text
ALERT_UPDATE|118|INC102|2|WARNING|Fire Controlled|Remain outside the building
```

If the new severity is `CRITICAL`, acknowledgement, retransmission, and duplicate-detection rules apply to the new Version.

## Closing an incident

Only the publisher that created an active incident may close it.

```text
CLOSE_ALERT|RQ#|Incident_ID|Reason
```

Example:

```text
CLOSE_ALERT|81|INC102|Incident resolved
```

The server changes the incident Status to `CLOSED`, increments its Version, and responds:

```text
ALERT_CLOSED|RQ#|Incident_ID
```

Example:

```text
ALERT_CLOSED|81|INC102
```

The server informs subscribers that received or currently match the incident:

```text
ALL_CLEAR|RQ#|Incident_ID|Version|Message
```

Example:

```text
ALL_CLEAR|125|INC102|3|Building reopened
```

Every `ALL_CLEAR` requires an `ALERT_ACK`, regardless of the incident's previous severity. The same timeout, three-attempt limit, and duplicate-detection rules apply.

## User safety status

A subscriber reports its latest status for an active incident using:

```text
STATUS_REPORT|RQ#|Incident_ID|Name|Status
```

Example:

```text
STATUS_REPORT|91|INC102|Alice|SAFE
```

Valid status values are:

```text
SAFE
NEED_HELP
LEFT_AREA
```

If accepted:

```text
STATUS_RECORDED|RQ#
```

Example:

```text
STATUS_RECORDED|91
```

If rejected:

```text
STATUS_REJECTED|RQ#|Reason
```

Example:

```text
STATUS_REJECTED|91|Unknown incident
```

The server stores only the most recent status reported by each client for each incident.

## Attachment discovery

A subscriber asks the Emergency Server where an attachment can be downloaded:

```text
ATTACH_REQ|RQ#|Incident_ID|File_Name
```

Example:

```text
ATTACH_REQ|91|INC102|evacuation_map.pdf
```

If the active incident, attachment, and publisher are available:

```text
ATTACH_INFO|RQ#|Incident_ID|Publisher_Name|IP_Address|TCP_Port|File_Name
```

Example:

```text
ATTACH_INFO|91|INC102|CampusSecurity|192.168.1.15|6100|evacuation_map.pdf
```

If the information is unavailable:

```text
ATTACH_DENIED|RQ#|Incident_ID|Reason
```

Example:

```text
ATTACH_DENIED|91|INC102|Publisher unavailable
```

Attachment discovery uses UDP. The Emergency Server only returns the publisher's endpoint; it does not transfer the file.

## Direct attachment transfer

After receiving `ATTACH_INFO`, the subscriber opens a TCP connection directly to the publisher.

The subscriber sends one newline-terminated request:

```text
GET_ATTACHMENT|RQ#|Subscriber_Name|Incident_ID|File_Name
```

Example:

```text
GET_ATTACHMENT|94|Alice|INC102|evacuation_map.pdf
```

If the request is valid, the publisher sends a newline-terminated header:

```text
ATTACH_DATA|RQ#|Incident_ID|File_Name|File_Size|Checksum
```

Example:

```text
ATTACH_DATA|94|INC102|evacuation_map.pdf|584271|3a42bc91
```

Exactly `File_Size` raw bytes follow the newline terminating the header. The file bytes are not UTF-8 text and are not separated using `|`.

The checksum is the lowercase hexadecimal SHA-256 checksum of the complete file.

After receiving and verifying the file, the subscriber sends:

```text
ATTACH_OK|RQ#|Incident_ID|File_Name
```

Example:

```text
ATTACH_OK|94|INC102|evacuation_map.pdf
```

If the transfer is incomplete or its checksum is incorrect:

```text
ATTACH_ERROR|RQ#|Incident_ID|File_Name|Reason
```

Example:

```text
ATTACH_ERROR|94|INC102|evacuation_map.pdf|Checksum mismatch
```

The publisher may also send `ATTACH_ERROR` without file data if the requested incident or file is unavailable.

The default TCP connection timeout is five seconds. The default read timeout is thirty seconds. A failed transfer may be attempted a maximum of three times. Every retry starts a new TCP connection and transfers the complete file again.

A publisher must be able to serve multiple subscribers concurrently without stopping its UDP control processing.

## Active incident synchronization

A registered client may retrieve currently active incidents that match its subscriptions. It opens a TCP connection to the Emergency Server and sends:

```text
GET_ACTIVE_ALERTS|RQ#|Name
```

Example:

```text
GET_ACTIVE_ALERTS|22|Alice
```

The server first sends:

```text
ACTIVE_ALERTS|RQ#|Number_Alerts
```

Example:

```text
ACTIVE_ALERTS|22|2
```

The server then sends exactly `Number_Alerts` newline-terminated records:

```text
ACTIVE_ALERT|Incident_ID|Version|Category|Location|Severity|Status|Title|Description|Attachment
```

Example:

```text
ACTIVE_ALERT|INC102|2|FIRE|HALL|WARNING|ACTIVE|Fire Controlled|Remain outside the building|evacuation_map.pdf
```

When no active incident matches, the server sends:

```text
ACTIVE_ALERTS|22|0
```

No incident records follow a zero count.

## Incident identifiers and versions

The server generates `Incident_ID` values using `INC` followed by a persisted increasing number, such as `INC102`.

The server stores the next available number so identifiers are not reused after a restart.

A new incident starts at Version `1`. Each accepted update or closure increments the Version atomically.

A client ignores an incident message with a Version lower than the newest Version it already knows. A message with the same Version is a duplicate. A higher Version replaces the client's older state.

## Authorization

The basic project trusts the role supplied during registration. Authentication is not required.

Role rules are still enforced:

- `SUBSCRIBER` may subscribe, receive alerts, report status, download attachments, and synchronize.
- `PUBLISHER` may publish, update, close, and serve attachments.
- `BOTH` may perform both sets of actions.
- Only the publisher that created an incident may update or close it.

## Malformed and invalid messages

If a request has a readable message name and `RQ#`, the server sends that request type's denial response with a reason.

If the message name or `RQ#` cannot be read, the receiver logs and discards the message because it cannot correlate a response.

Unknown message names, missing fields, extra fields, invalid numbers, invalid enum values, and oversized messages are malformed.

A malformed message must not change stored state or terminate a server thread.

## Restart and re-registration

The server persists user profiles, subscriptions, incidents, attachment metadata, status reports, and delivery information.

After a server restart, persisted clients are considered inactive until they register again.

The first valid registration for a persisted name reactivates that profile and updates its network endpoint. A conflicting registration for a name that is already active is denied.

Temporary sockets and expired timers are not restored. Active clients can use `GET_ACTIVE_ALERTS` to recover the current incident state.

## Concurrency rules

The UDP receiver must not wait for acknowledgement timers or file transfers.

Incoming UDP requests are handed to workers. Critical-alert retransmissions use a scheduler so several timers can run concurrently.

The Emergency Server handles TCP synchronization connections concurrently. Publisher clients handle attachment connections concurrently.

Updates to registration, subscriptions, incidents, acknowledgements, and status records must be atomic.

## Persistence rules

State-changing operations are written to persistent storage before their success response is sent.

A snapshot is written to a temporary file and then atomically replaces the previous complete snapshot.

On startup, the server loads the latest complete snapshot. An incomplete temporary snapshot is ignored.

Attachment file contents are never stored by the Emergency Server.
